# Alembic database migrations

TutorInn keeps Alembic configuration and versioned Python revisions in this directory. Application code remains under `backend/app/`; migration files must not be placed inside the application package.

## Configuration

- Configuration: `backend/alembic.ini`
- Environment and SQLAlchemy metadata: `backend/alembic/env.py`
- Revision scripts: `backend/alembic/versions/`
- Database URL: `DATABASE_URL` (or `POSTGRES_URL`), using the same resolution as the application in `backend/app/database.py`

The configuration uses paths relative to `alembic.ini`, so commands work from the repository root or the backend directory when the config path is supplied.

## Common commands

Run from the repository root:

```bash
# Show the current revision recorded in the configured database
alembic -c backend/alembic.ini current

# List known migration heads
alembic -c backend/alembic.ini heads

# Create a new revision from model metadata
alembic -c backend/alembic.ini revision --autogenerate -m "describe the schema change"

# Review and edit the generated revision, then apply it
alembic -c backend/alembic.ini upgrade head
```

Or run from `backend/` with `alembic current`, `alembic heads`, and so on.

Always inspect autogenerated revisions before applying them. Autogeneration is a draft, not a substitute for reviewing constraints, indexes, data migrations, and destructive operations. Add explicit data backfills where required.

## Existing Supabase databases and baseline

Revision `20261116_0001` is a **no-op baseline marker** for databases whose schema already exists. It intentionally does not create or drop application tables.

Do not run `upgrade head` expecting this baseline to create the current TutorInn schema. Before recording the baseline on an existing database:

1. Back up the database.
2. Compare its actual schema with the SQL migration history in `supabase/migrations/` and the SQLAlchemy models.
3. Resolve any schema differences first.
4. Only when the existing schema is confirmed to match the baseline, record it with:

```bash
alembic -c backend/alembic.ini stamp 20261116_0001
```

Stamping records the revision; it does not execute the revision's DDL. Never stamp an unverified database, and do not run this against production without an approved backup and migration plan.

Supabase SQL migrations remain part of the Supabase deployment workflow. Do not independently apply the same schema change through both Supabase SQL migrations and Alembic. Coordinate each schema change so the deployment has one reviewed migration path and the two histories cannot drift.

## Runtime initialization note

The FastAPI lifespan currently calls `initialize_database()` for the existing MVP startup behavior. That function still contains `create_all` and compatibility column additions. Introducing Alembic does not silently remove or replace that behavior. Any later change to make Alembic the sole schema lifecycle mechanism must be a separate, tested change with a safe rollout plan for existing databases.
